# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Added
- **CI/CD pipeline** (`.github/workflows/pr-checks.yml`, `.github/workflows/deploy.yml`): replaced the deploy-on-the-same-host-as-prod flow with build-once-promote — images are built and pushed to a local Docker registry (`infra/registry/`), validated end-to-end in an ephemeral, resource-capped staging stack (`docker-compose.staging.yml`, its own ports/network/volumes) running migrations, integration tests, and Playwright e2e, and only then promoted to prod (`scripts/promote-to-prod.sh`). A failed post-deploy smoke check triggers an automatic rollback (`scripts/rollback-prod.sh`) to the previously-promoted images. Added a `pr-checks.yml` workflow (lint + unit tests) as a required gate before merging to `main`, where none existed before.
- **`.github/PULL_REQUEST_TEMPLATE.md`** and a Conventional Commits / changelog convention documented in `CLAUDE.md`, so future decisions are easier to recover (used by Repowise's decision archaeology).
- **`deploy/ansible/roles/runner/`**: codifies the manual VPS setup the new CI/CD pipeline needed (ACLs granting the runner user access to `app_dir` and the deploy key, its SSH config, git `safe.directory`, npm/Playwright CI caches, and the Docker daemon's `insecure-registries` entry) so a rebuilt or migrated box doesn't silently lose access the pipeline depends on. Documented alongside two new `CLAUDE.md` conventions: add a regression test with every bugfix, and reflect manual server changes in Ansible in the same PR.
- **CLAUDE.md**: added a "Keeping Repowise current" convention — run `repowise update` after pushing a change (free, index-only: refreshes the dependency graph, git history, and CHANGELOG-derived decision records) so `get_why`/`get_risk`/`get_context` don't answer from a stale snapshot. `--docs` (LLM-backed page regeneration) is called out as a deliberate, token-costing action, not a default.
- **CLAUDE.md**: added a "Recording architectural decisions" convention — record real architectural choices directly via `repowise decision add` in the same PR. CHANGELOG-derived decision mining turned out to only run during the initial `repowise init`, not incrementally on `update` (confirmed empirically: a full `--docs` run produced 18 new wiki pages but zero new decisions from a session's worth of CHANGELOG entries) — manual recording is the only way to keep `get_why` answering with real context until that's fixed upstream.
- **`scripts/promote-to-prod.sh`**: takes a `pg_dump` of prod's database right before running migrations, keeping the last `DB_BACKUP_RETENTION` (default 10) under `.deploy-state/db-backups/`. `rollback-prod.sh`'s own header comment already says it deliberately doesn't touch the database since Medusa migrations are forward-only — until now that "needs manual DB intervention" case had nothing to restore from. Restore (`scripts/restore-db-backup.sh`, `docs/db-restore-runbook.md`) is deliberately manual and interactive (typed confirmation), never wired into the automatic rollback path: an automatic restore triggered by a flaky smoke test would silently discard any real order/account written since the backup.
- **`docs/db-restore-runbook.md`**: added a "reconcile what the database doesn't know about" section — restoring a backup reverts Postgres, but not physical fulfillment already dispatched/received (`backend/src/workflows/steps/{generate-pick-list,dispatch-order,receive-purchase-order}.ts`) or order-confirmation notifications already sent (`order-placed.ts` subscriber, `notify-agent` route) for orders that vanish after the restore — both need manual human follow-up the system has no record of afterward.
- **`.github/workflows/deploy.yml`**: added `paths-ignore` (`**/*.md`, `docs/**`, `.claude/**`) to the `push` trigger so doc-only commits to `main` skip the whole build+staging+promote pipeline — nothing in a markdown-only change can affect a running deploy, and the pipeline is the most expensive workflow in the repo (full staging stack + e2e). Deliberately **not** applied to `pr-checks.yml` (the other CI workflow): it's a required status check for merging to `main`, and a workflow that never triggers on a path-filtered PR can leave that PR permanently stuck waiting for a check that will never report — a known GitHub Actions branch-protection footgun. `pr-checks.yml` stays cheap enough (lint + unit tests, no staging stack) that always running it on doc-only PRs isn't worth that risk.
- **`.github/workflows/deploy.yml`**: added a warn-only infrastructure drift-check (`ansible-playbook --check --diff` against `deploy/ansible/site.yml`) right after syncing the checkout. `CLAUDE.md` already requires manual server changes to be ported back into the Ansible roles, but nothing verified the live VPS actually matched what those roles declare — drift could (and did, in practice) accumulate silently. Deliberately warn-only (`::warning::`, never fails the job): unlike the app deploy, infra changes here touch firewall/sudoers/Docker daemon with no staging environment and no automatic rollback — auto-applying them unattended on every push risks a self-inflicted lockout (e.g. a bad firewall rule or malformed sudoers file), so fixing real drift stays a deliberate `ansible-playbook site.yml --ask-vault-pass` run from an operator's laptop. Runs locally on the runner (new `deploy/ansible/inventory.ci.ini`, `ansible_connection=local`) rather than over SSH, using a narrowly-scoped sudoers rule (`roles/runner`, NOPASSWD limited to the `ansible-playbook` binary, not `ALL`) instead of handing the runner the operator's root SSH key. The vault password is read from a new GitHub Actions secret (`ANSIBLE_VAULT_PASSWORD`) — the first GitHub Secret this pipeline uses — rather than a password file living next to `vault.yml` on the same disk it protects. Also added `no_log: true` to the two `roles/app` templates that render real secrets (`root.env.j2`, `backend.env.j2`); without it, `--diff` would print those files' contents — including the admin password, JWT/cookie secrets, and R2 keys — straight into the CI log the first time either one actually drifted.
- **`scripts/backup-db.sh`, `deploy/ansible/roles/backup/`**: recurring, off-VPS database backups, closing two gaps in the existing deploy-triggered backup (`promote-to-prod.sh`): no backup is taken between deploys, and every backup lived on the same disk as the live database, so losing the VPS lost both at once. Extracted the inline `pg_dump` from `promote-to-prod.sh` into a shared script with two independent, non-overlapping pools — "merge" (every deploy, local-only, `MERGE_BACKUP_RETENTION_DAYS`, never touches the network so a merge to `main` can't depend on home connectivity) and "scheduled" (a new systemd timer, `NAS_BACKUP_INTERVAL_HOURS`, `NAS_BACKUP_RETENTION_DAYS`, mirrored off-site) — both pruned by file age rather than file count, since cadence is irregular (deploys) for one pool and itself a tunable interval for the other. Off-site destination is the operator's own Synology NAS, not Cloudflare R2 (avoids consuming R2's free tier), reached over a WireGuard split-tunnel (new `backup` Ansible role; `AllowedIPs` deliberately excludes `0.0.0.0/0` so the VPS's own production traffic is never rerouted) into the NAS's native rsync daemon account rather than SSH — this NAS restricts SSH/terminal login to the `administrators` group with no per-user override, confirmed empirically (`ssh -vv` showed password auth succeeding, then a second-stage `Permission denied`). Each dump is integrity-checked (`gzip -t`) immediately after creation; a corrupt dump is deleted and the script exits non-zero, which aborts the deploy when called from `promote-to-prod.sh` (`set -euo pipefail`) instead of proceeding without a trustworthy pre-migration backup. Encryption at rest, failure alerting, and an automated restore drill (beyond the gzip integrity check) were identified but deliberately deferred to a future iteration, not bundled into this change.
- **`infra/monitoring/configs/grafana/provisioning/alerting/{contact-points,notification-policies}.yml`, `scripts/backup-db.sh`**: mail alerts for both the host-monitoring stack and backup failures, the two items deferred from the backups change above. Grafana's 3 existing alert rules (target down, memory, disk) evaluated correctly but had nowhere to notify — `infra/monitoring/configs/grafana/README.md` already flagged this exact gap. Added a 4th rule (`erp-host-cpu-high`, >85% for 10m) and a `resend-email` contact point routed through Grafana's own SMTP (`GF_SMTP_*` in `infra/monitoring/compose.yml`) pointed at Resend's SMTP relay, instead of a webhook contact point backed by a custom relay service — Resend already supports SMTP natively, so this needed zero new components. The recipient address is read via Grafana's `$__env{}` provisioning macro (`MONITORING_ALERT_EMAIL` in `infra/.env`, not committed) rather than hardcoded into the tracked YAML. `monit` was considered and rejected as an alternative for the CPU/memory/disk alerting itself — it would duplicate metrics node-exporter already collects, running a second monitoring path in parallel for no benefit. Separately, `backup-db.sh` now has a `notify_failure`/`trap ... ERR` pair (requires `set -Eeuo pipefail`, not just `-eu`, for the trap to fire reliably inside its functions) that mails `BACKUP_ALERT_EMAIL` (new, `deploy/ansible/group_vars/all/vars.yml`/`root.env.j2`) on any failure — reuses the same Resend HTTP API call shape as `backend/src/subscribers/invite-created.ts` and the credentials already in `backend/.env`, rather than routing through Prometheus (would need a Pushgateway for what's a one-off job event, not a continuous metric).

  **Verified end-to-end with a real send**: a test via the production `RESEND_API_KEY` (same call shape as `notify_failure`) confirmed `Delivered` in Resend's dashboard and the mail did arrive at both Gmail recipients — but landed in spam, not inbox (domain is `Verified` in Resend; likely cold-sender reputation, since this domain had never sent to these addresses before). Mark the first real alert as "not spam" in Gmail for both recipients so future ones land in inbox — no code or config change needed, this is sender-reputation warm-up, not a bug.

- **`deploy/ansible/roles/infra/`, `scripts/send-resend-mail.sh`**: brings `infra/.env` (nginx-proxy-manager's MariaDB password, Grafana/Portainer admin credentials, plus the Resend vars from the previous entry) under Ansible — the one `.env` in this repo still hand-edited on the VPS. `repowise get_why` confirmed this was never a deliberate choice: `infra/monitoring` was added before Ansible existed at all in this repo, and the later "make everything reproducible" effort never came back to close that gap. The new role renders `infra/.env` from a template (reusing the existing `vault_resend_api_key`/`vault_resend_from`, no new Resend secret needed) and recreates the `erp-infra`/`erp-monitoring` compose projects only when that file actually changed — same pattern as `roles/backup` only restarting `wg-quick@wg0` on a real config change. Must run before `roles/runner`, which narrows `infra/.env`'s ACL to read-only the same way it already does for the other three `.env` files. Extracted the Resend `curl`/`jq` call (previously duplicated between `invite-created.ts` and `backup-db.sh`'s `notify_failure`) into `scripts/send-resend-mail.sh` once a 3rd caller (the drift-check below) needed the same shape — `backup-db.sh` now delegates to it.
- **`.github/workflows/deploy.yml`**: the infrastructure drift-check's 3 outcomes (check didn't complete, failed/unreachable dry-run, real drift detected) previously only wrote a `::warning::` to the Actions log — easy to miss without someone actively watching that run. Now also emails `MONITORING_ALERT_EMAIL` via `scripts/send-resend-mail.sh` for all 3, reading credentials from the now-Ansible-managed `infra/.env`. The mail body is the same text as the `::warning::` plus a link to the run — deliberately never the raw `ansible-playbook --diff` output, to avoid ever having to reason about whether some future task without `no_log` made that output unsafe to email. Degrades silently to just the existing `::warning::` if `infra/.env` doesn't have Resend configured yet (e.g. before this PR's first real apply). Doesn't change the existing warn-only philosophy — still strictly manual to actually apply a fix.

### Fixed
- **`docs/deploy.md`**: described a workflow (`deploy-to-rpi.yml`, `git pull` + `compose-up.sh`, manual `git reset --hard` rollback) that no longer exists — superseded by the build-once-promote `deploy.yml` documented in the CHANGELOG entry above. Following the old "Rollback manual" section during a real incident would have done something other than what the pipeline actually does (no image-tag swap, an unnecessary rebuild, no DB backup awareness). Also fixed every reference to the prod checkout path (`/home/akwiek/code/ERP`, a dev laptop path) to the real `DEPLOY_DIR` (`/root/ERP`), and pointed initial-server-setup instructions at `deploy/ansible/` instead of duplicating (and silently diverging from) it.
- **`README.md`** / **`DESIGN.md`**: translated to English (see the new `CLAUDE.md` convention below) — `DESIGN.md` also had every code-reference link missing the `storefront/` path segment, hardcoded as an absolute dev-laptop path (`/home/akwiek/code/ERP/src/...`), stale since the monorepo restructure that moved the frontend into `storefront/`. `README.md` still pointed at the retired `deploy-to-rpi.yml` workflow and `--env-file .env` instead of `infra/.env` for the Nginx Proxy Manager compose invocation.
- **`deploy/ansible/group_vars/all/vars.yml`, `roles/app/templates/backend.env.j2`**: a `--check --diff` dry-run against the real VPS (the first time `site.yml` was ever reconciled against it — it had only ever been hand-provisioned) showed the playbook would have rewritten `STORE_CORS`/`ADMIN_CORS`/`AUTH_CORS`/`MEDUSA_ADMIN_URL` to `http://<ip>` instead of the real `https://*.gleeze.com` domains, forced `MEDUSA_FORCE_INSECURE_COOKIES=true` on a site that actually serves HTTPS (`false` in reality), and flipped `SEED_DEMO_DATA` from the real `false` to `true` — reseeding the demo catalog against the live production database. The playbook predates the migration to domain+HTTPS via Nginx Proxy Manager and was never updated afterward. `storefront_origin`/`backend_url` are now fixed real domains instead of derived from `public_host`+port (which stays, used only for the on-box smoke checks and UFW rules); added `pos_origin` (missing from CORS entirely) and a `medusa_force_insecure_cookies` toggle defaulting to `false`. Also confirmed (via checksum against `infra/.env`, git history, and `scripts/compose-up.sh`'s `--env-file infra/.env`) that the live root `.env`'s `NGINX_DB_PASSWORD`/`MONITORING_ADMIN_*`/`PORTAINER_ADMIN_PASSWORD_HASH` lines are unused leftovers from before infra's env was split out — safe for the template to drop them.
- **`deploy/ansible/roles/runner/`**: the first real (non-`--check`) run of `site.yml` against the VPS revealed two ACL-driven false-positive "changed" loops, found by running `--check --diff` again right after — `git`/`ssh` reject a private key with *any* group/other bits regardless of whether the access is really scoped to a named ACL entry, so sharing the deploy key with `github-runner` via `setfacl` (instead of a separate copy) widened its ACL mask and broke root's own "Clone or update the repository" task the moment the grant ran; separately, the recursive `setfacl -R u:github-runner:rwx {{ app_dir }}` grant covered the rendered `.env` files too, so the same mask-widening fought `roles/app`'s `mode: "0644"` every run even though `github-runner` only ever greps credentials from them (never writes). Fixed by giving the runner its own deploy-key copy (re-rendered from the same vault secret each run, so rotation stays in sync without the ACL) and narrowing its access on the three `.env` files to read-only after the recursive grant. Confirmed via `getfacl` and a clean `--check --diff` (`changed=1`, `failed=0` — only Docker's GPG key, which always re-reports regardless of real drift) that this was the last source of perpetual false drift.
- **`deploy/ansible/README.md`** / **`docs/deploy.md`**: both still described the pre-reconciliation reality fixed by the two entries above — `README.md` said the stack served "over plain HTTP via its public IP" and that the runner role "reads the shared deploy key over SSH" (it now gets its own copy, see above), and its "First-time setup" section falsely implied a vault was already populated "for the current box" when none had ever existed. Rewrote both to describe the real HTTPS-via-Nginx-Proxy-Manager architecture, the runner's separate deploy-key copy, and explicit instructions to pull real values off the live server before first encrypting a vault rather than inventing new ones (which would lock out whatever already depends on the old secrets). Also documented the new `ANSIBLE_VAULT_PASSWORD`/`ANSIBLE_VAULT_FILE` CI secrets in both docs, and pointed "Deploy / migrate" at `--check --diff` first.
- **`.github/workflows/deploy.yml`**: the drift-check step only ever looked for a `changed=N` substring anywhere in `ansible-playbook`'s output to decide whether to warn — if the command failed *before* reaching its PLAY RECAP (a rotated vault password no longer matching the secret, a broken sudoers rule, a playbook syntax error, an unreachable host), there was no `changed=` line at all, the grep came back empty, `${changed:-0}` silently read that as `0`, and the step reported nothing — indistinguishable from "ran cleanly, no drift". The one automated check that exists for infrastructure drift could be broken for weeks without anyone noticing, because its own failure mode looked identical to success. Now isolates the actual recap line (`<host> : ok=.. changed=.. unreachable=.. failed=..`) before parsing it, and treats its absence as a distinct outcome — a `::warning::` saying the check itself didn't complete and drift status is unknown, separate from the existing "drift detected" warning. Also now flags `failed`/`unreachable` > 0 in the recap (a partial failure on `--check` itself), previously ignored entirely since only `changed` was read.
- **`storefront/e2e/_customer.ts`**: `PUBLISHABLE_KEY` typed as `string` (was `string | undefined`) — `next build` type-checks `e2e/` since `tsconfig.json` doesn't exclude it, and the old module-level throw guard wasn't narrowed across the functions declared later in the file. This blocked every `web` image rebuild, not just CI.
- **`storefront/src/app/checkout/__tests__/page.ui.test.tsx`**: updated step assertions for the 3-step checkout flow (shipping method is no longer its own step) — stale since the checkout refactor, never caught because no workflow ran storefront unit tests before `pr-checks.yml`.
- **.github/workflows/deploy.yml**: "Build and push web (staging-flavored env)" step was missing the `IMAGE_TAG` env var that every other step touching `docker-compose.staging.yml` sets — `sync-medusa-env.sh --project erp-staging` failed to parse the compose file (`IMAGE_TAG` is a required interpolation for `backend`/`backend-init`/`web`/`pos`), surfacing as the misleading "db service is not available" error even though the staging `db` container was healthy
- **.github/workflows/deploy.yml**: "Backend integration tests against staging" step only set `DATABASE_URL`, but `@medusajs/test-utils`' `MedusaTestRunner` (used by every `integration-tests/http/*.spec.ts` suite) creates/drops its temp database via `pg-god`, which reads the split `DB_HOST`/`DB_PORT`/`DB_USERNAME`/`DB_PASSWORD` vars instead — left unset, it defaulted to Postgres' default port 5432 (nothing listening there) instead of staging's `5532`, failing every HTTP integration suite with "Error initializing database"
- **.github/workflows/deploy.yml**: "Backend admin e2e" and "Storefront e2e" steps logged in with the e2e suites' fallback credentials (`admin@aurelia.com` / `supersecret`), but the staging admin user was actually created by `backend-init` using `MEDUSA_ADMIN_EMAIL`/`MEDUSA_ADMIN_PASSWORD` from `backend/.env` — a different real secret, not the fallback. Both steps now grep those two values out of `backend/.env` and forward them as `ADMIN_EMAIL`/`ADMIN_PASSWORD`, the names the e2e suites actually read.
- **.github/workflows/deploy.yml**: the e2e steps' first attempt at reading `backend/.env` used `source`, which failed with a bash syntax error — `.env` files follow dotenv-style parsing, not POSIX shell syntax, and `RESEND_FROM`'s unquoted "Aurelia &lt;invitaciones@...&gt;" value is parsed by bash as redirection. A second attempt (`grep`/`cut` on the host) avoided that, but admin login still failed in staging even though `backend-init`'s logs confirmed the user was created successfully. Replaced with `docker run --env-file backend/.env` — the same dotenv-style parser `docker-compose.staging.yml` itself uses to create the user — remapping `MEDUSA_ADMIN_EMAIL`/`MEDUSA_ADMIN_PASSWORD` to `ADMIN_EMAIL`/`ADMIN_PASSWORD` inside the container, guaranteeing both sides parse the same file the same way.
- **.github/workflows/deploy.yml**: admin e2e login kept failing even with the credential-passing fix above, because a `workflow_dispatch` run cancelled mid-flight while iterating on these fixes skipped "Tear down staging" (`down -v`) — `docker-compose.staging.yml` declares no named volume for `db`, but the cancelled run's anonymous volume survived and got reused by the next run's `up -d db`, carrying over an admin user/password from an earlier, unrelated test attempt. Added a defensive "Clean up any leftover staging stack from a previous run" step (`down -v --remove-orphans`) right after the checkout, so every run starts from a guaranteed-empty database regardless of how the previous run ended.
- **docker-compose.staging.yml**: admin e2e login still failed even against a clean database with correct credentials — `backend/.env` is tuned for prod, which serves over real HTTPS (`MEDUSA_FORCE_INSECURE_COOKIES=false`), but staging serves over plain HTTP on `127.0.0.1`. The login response's auth cookie came back `Secure`-flagged, which browsers silently drop on a non-HTTPS origin, bouncing every authenticated request back to `/app/login` regardless of how correct the submitted credentials were. Added an `environment` override on the staging `backend` service forcing `MEDUSA_FORCE_INSECURE_COOKIES=true`, without touching the real `backend/.env`.
- **.github/workflows/deploy.yml**: with login fixed, "Storefront e2e against staging" failed ~20 specs with no products visible anywhere (catalog, home, cart, checkout) even though `seed-e2e.ts` logged successful creation. Root cause not yet confirmed — the pipeline never captured the `web` service's own container logs, where a `[medusa-env]` stale-key warning or a proxy/rewrite error would actually show up. Added a "Dump staging container logs (on failure)" step (`docker compose logs backend`/`web`) right before teardown, so the next failure carries direct evidence instead of requiring a live manual repro.
- **scripts/sync-medusa-env.sh**: confirmed via a Playwright trace's browser console — every store API call from the staging storefront was being blocked by CORS, because it was calling `https://backoffice.aurelia.gleeze.com` (prod's real domain) directly instead of staging's own backend. `storefront/.env` is the same physical file prod uses, where `NEXT_PUBLIC_MEDUSA_BACKEND_URL` is intentionally pinned to that absolute prod URL — this script only ever updated the publishable key/region/country vars, never touching that one, so staging builds silently inherited it. Now clears `NEXT_PUBLIC_MEDUSA_BACKEND_URL` when run with `--project` (staging only), falling back to the relative `/api/medusa` proxy (same-origin, no CORS) per `src/lib/medusa.ts`'s own fallback logic; the default (prod) path is untouched.
- **scripts/sync-medusa-env.sh**: with CORS fixed, the storefront's `/api/medusa` proxy itself failed with `ECONNREFUSED 127.0.0.1:9000` — `next.config.ts`'s `rewrites()` resolves `MEDUSA_INTERNAL_BACKEND_URL` into `routes-manifest.json` at Next.js **build time**, not at container startup, so `docker-compose.staging.yml`'s runtime-only `environment: MEDUSA_INTERNAL_BACKEND_URL: http://backend:9000` override never took effect — the build fell back to `next.config.ts`'s own default (`http://localhost:9000`), which doesn't resolve to anything inside the `web` container. Prod never hit this because it bypasses the proxy entirely via the absolute `NEXT_PUBLIC_MEDUSA_BACKEND_URL`. Now writes `MEDUSA_INTERNAL_BACKEND_URL=http://backend:9000` into `storefront/.env` itself when run with `--project` (staging only, same gate as the fix above), so it's available at build time; `promote-to-prod.sh` calls this script with no `--project` flag, so prod's build path is unaffected.
- **storefront/e2e/_customer.ts** / **.github/workflows/deploy.yml**: `account.spec.ts`'s second test (login as an API-provisioned customer) defaulted `BACKEND_URL` to `http://localhost:9000` for its direct admin/store API calls. On the self-hosted runner that port is prod's own backend (`docker-compose.yml`'s `127.0.0.1:9000:9000`), not staging's (`9100`) — `deploy.yml`'s "Storefront e2e against staging" step only set `BASE_URL` (the browser's target), never `BACKEND_URL`, so the test silently created/captured/delivered a real order and customer in prod via prod's real admin credentials, then cleaned them up in `afterEach` (same wrong URL), before failing because the *browser* login (against staging, which never saw that customer) couldn't find the account. Removed the dangerous fallback — `BACKEND_URL` is now required and throws if unset — and added `-e BACKEND_URL=http://127.0.0.1:9100` to the workflow step so the helper points at staging like the browser does.
- **storefront/e2e/cart.spec.ts**: "cart drawer shows added product", "can navigate to checkout from cart drawer" intermittently failed in CI with the "Abrir carrito" click intercepted by an overlapping element, then permanently invisible on retry. Root cause: `cart-provider.tsx` rehydrates the cart from the backend asynchronously on every mount (`sdk.store.cart.retrieve`), and `site-header.tsx` swaps between two mutually-exclusive cart-trigger buttons (a mobile icon, a desktop "Finalizar compra N" pill) once `totalItems` flips from 0 to its real value. Clicking immediately after `page.goto("/")` raced that hydration — if the swap landed mid-click, the originally-targeted button had already become permanently hidden for the rest of the test. Two other tests in the same file (`cart state persists across page navigation`, `can remove item from cart`) already carried a `waitForTimeout(1500)` fix for this exact race; it just hadn't been applied to these two. Brought them in line with the existing pattern.
- **docker-compose.staging.yml** / **.github/workflows/deploy.yml**: the `BACKEND_URL` incident above was possible because the 3 ad-hoc `docker run` test containers used `--network host` (chosen in `bef739f` purely so they could reach staging's host-bound ports via `localhost`, without needing the job to know Compose's internal network — a convenience choice, not a deliberate decision to share the host's network with prod). That meant any wrong default — not just the one already found — could silently reach whatever's listening on the real host ports, including prod on this same self-hosted runner. `docker-compose.staging.yml` now declares its network explicitly (`networks.default.name: erp-staging-net`) instead of relying on Compose's implicit `<project>_default` naming, and the 3 `docker run` steps join it (`--network "$STAGING_NETWORK"`) instead of the host's, addressing services by name (`db:5432`, `backend:9000`, `web:3000`) instead of `localhost:<host-port>` — a missing/wrong var now fails with `ECONNREFUSED`/DNS error instead of silently hitting prod, because there's no network path to prod's ports from inside that network at all. Also removed the same dangerous `|| "http://localhost:9000"` / `|| "http://localhost:7358"` fallbacks from `backend/e2e/playwright.config.ts` and `storefront/playwright.config.ts` (same class of landmine, previously inert only because `deploy.yml` always overrode them by hand).
- **storefront/e2e/_customer.ts** / **.github/workflows/deploy.yml**: with the above fixed, "Storefront e2e against staging" failed `registerCustomerApi` with `400 "A valid publishable key is required"` — `_customer.ts`'s publishable-key fallback (`readDevEnvVar`) reads `storefront/.env.development`, but `sync-medusa-env.sh --project erp-staging` only ever writes `storefront/.env`, so the helper sent whatever stale key was left in `.env.development` from an earlier checkout (likely prod's), which staging's freshly-bootstrapped database had never seen. Added `--env-file storefront/.env` to the "Storefront e2e against staging" step so the container gets the just-synced `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` directly.
- **.github/workflows/deploy.yml**: "Backend integration tests against staging" still failed on `$STAGING_NETWORK` even though DNS/raw TCP/`pg.Client` connect+create-database all worked instantly from a manual repro inside the exact same container — `@medusajs/test-utils`' `MedusaTestRunner` (`inApp: true`, used by every `integration-tests/http/*.spec.ts` suite) hung for 60s twice (`KnexTimeoutError`) on every single spec file booting its own in-process Medusa app, then died at its 180s hook timeout.
